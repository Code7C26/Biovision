# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

GRANEX is an Android app (Kotlin, Jetpack Compose, Material 3) for Argentine agriculture: FX/financial quotes, ROFEX futures, Rosario grain market prices, agro-weather/radar, satellite field (lote) monitoring and agro news. It was generated by Google AI Studio. UI strings, identifiers and comments are mostly in **Spanish**; keep new code consistent with that.

Modules:
- `:app` is the Android app.
- `:shared` is Kotlin Multiplatform (android + js + wasmJs) with the pure logic, Ktor clients, preferences and the Supabase backend (accounts, `lotes` sync, Storage). It has no Compose on purpose.
- `:webApp` is the web version: a PWA built with Compose Multiplatform for Wasm with a JS fallback.

See `docs/web/MIGRACION_KMP.md` for the migration plan and phases, `docs/web/DESPLIEGUE.md` for hosting, and `docs/backend/SUPABASE.md` for the backend setup.

## Build & test

Build via Android Studio (open the root folder) or the Gradle wrapper (`./gradlew ...`). AGP 9.1, Kotlin 2.2, compileSdk/targetSdk 36, minSdk 24, Java 11. Dependency versions live in `gradle/libs.versions.toml`.

- Build debug APK: `gradle :app:assembleDebug`
- Unit tests (JVM, Robolectric): `gradle :app:testDebugUnitTest`
- Single test: `gradle :app:testDebugUnitTest --tests "com.example.ExampleUnitTest"`
- Screenshot tests (Roborazzi): `gradle :app:recordRoborazziDebug` / `gradle :app:verifyRoborazziDebug`; images are written to `app/src/test/screenshots/`
- Instrumented tests: `gradle :app:connectedDebugAndroidTest`
- Shared tests: `gradle :shared:allTests` runs `commonTest` on the JVM (Android host test), Node/JS and Node/Wasm. Node.js is downloaded by the Kotlin plugin from the ivy repos declared in `settings.gradle.kts`, which is why `repositoriesMode` is `PREFER_SETTINGS`.
- Web: `gradle :webApp:wasmJsBrowserDevelopmentRun` for the dev server; `gradle :webApp:distribucionPwa` builds the deployable PWA into `webApp/build/dist/pwa`.

Build setup gotchas:
- The `debug` build type signs with `${rootDir}/debug.keystore` (gitignored, not present). Per the README, remove `signingConfig = signingConfigs.getByName("debugConfig")` from `app/build.gradle.kts` (or provide the keystore) to build locally.
- `google-services.json` is absent; the google-services plugin is configured to only WARN.
- Secrets come from `.env` (fallback `.env.example`) via the Secrets Gradle Plugin and surface as `BuildConfig.*` fields. Today the only one is `MAPTILER_API_KEY`.
- **Supabase** URL and public key come from `local.properties` (`supabase.url`, `supabase.anonKey`) or the env vars `SUPABASE_URL` and `SUPABASE_ANON_KEY`, read by `gradle/supabase.gradle.kts`, which both `:app` and `:webApp` apply. Android gets them as `BuildConfig.SUPABASE_*`. The web gets a generated `ConfiguracionSupabaseWeb`, and its CSP gets the project origin through the `__ORIGEN_SUPABASE__` placeholder in `index.html`. Empty means no backend: the app behaves as local-only. User credentials (Copernicus) must never be compiled in: they are entered in Ajustes. Read API keys through `data/remote/api/ApiKeys.kt`, which returns null for missing/placeholder values so callers fall back to demo data instead of sending a bad key. Adding a new key = add a placeholder to `.env.example` and expose it in `ApiKeys`.

## Security conventions

- Never hardcode credentials or real keys; `BuildConfig` values are extractable from the APK, so keys must be restricted (MapTiler key restricted to the `MAP_WEBVIEW_ORIGIN` origin used by the satellite WebView). Don't put a Gemini key in the app: use Firebase AI Logic + App Check or a backend.
- User secrets (the Copernicus client secret) go through `WeatherNotificationService.leerSecreto/guardarSecreto`, which encrypt them with `utils/CredentialCipher` (AES-256-GCM, non-exportable Android Keystore key). Plain-text leftovers are migrated at startup (`cifrarSecretosPendientes`), and the prefs file is excluded from backups in `res/xml/backup_rules.xml` / `data_extraction_rules.xml`. Don't add `security-crypto`/EncryptedSharedPreferences (deprecated); new secrets must be added to `CLAVES_SECRETAS`.
- Secret inputs use `ui/components/CampoSecreto` (hidden by default, eye toggle, `KeyboardType.Password`, no autocorrect); user names and client IDs use `CampoIdentificador`. Never keep secrets in `rememberSaveable`.
- **Supabase:**
  - Only the public key (`anon` or `sb_publishable_`) may ship. The build script and `ConfiguracionSupabase.desde` reject a `service_role` or `sb_secret_` key, because that key bypasses RLS.
  - Data is protected by the RLS policies in `supabase/migrations/`. Every new table needs RLS enabled plus policies keyed on `auth.uid()`.
  - Auth enforces the same password rule as `ValidacionCuenta` (≥ 8 characters with letters and digits: `password_min_length`, `password_required_characters`), so a modified client can't create a weak password. Leaked-password (HIBP) checks need the Pro plan and are off. Security advisors (2026-11-18): `credenciales_estacion` has RLS without policies on purpose (service role only); `registrar_pedido_sentinel()` is callable through RPC but only raises the caller's own daily count.
  - The Android session is stored by `SesionEnAjustes`, encrypted with `CredentialCipher`, in `granex_sesion.xml`, which is excluded from backups.
  - The Android Supabase HTTP engine is `ktor-client-android`, not OkHttp: Ktor 3's OkHttp engine brings OkHttp 5, which clashes with Retrofit's OkHttp 4.
  - `:app` pins `lifecycle-process` with `strictly` to the app's Lifecycle 2.8.7. supabase-kt asks for 2.9.4, which drags Lifecycle to 2.9 and Compose from 1.7 (BOM 2024.09) to 1.9. That silently changed password-field semantics (caught by `CampoSecretoTest`). Upgrading Compose is a separate decision.
  - supabase-kt is 3.2.6, the last release built with Kotlin 2.2.21 and Ktor 3.3. 3.3+ needs Kotlin 2.3 or newer.
- **Account required:** with a backend nobody uses the app (Android or web) without a session. Android: `AccesoGranex`; web: `GranexWeb` shows only `PantallaCuenta` while `SinSesion`. A release build without Supabase fails (`app/build.gradle.kts`), since without a backend the app opens in local mode. The gate is UI: the protection of user data is RLS plus Edge Functions that require a real user; what the app shows without data (quotes, weather) comes from public APIs anyway.
- **Logout and account deletion wipe the device** before dropping the session (otherwise the Activity restart would cancel the wipe): lots (`SincronizadorLotes`), soil/yield/dose files, Copernicus credentials and any old reMarkets leftovers (`WeatherNotificationService.borrarCredencialesTerceros`), campaign image cache and the profile copy. Logout is blocked while soil/yield data are unsent (`antesDeCerrarSesion`). After logout `AccesoGranex` restarts the Activity so no screen ViewModel keeps the previous account in memory.
- Backups exclude the session, credentials prefs, `granex_sync.xml`, the Room DB, `files/agronomia/` and `files/agenda/` (`backup_rules.xml`, `data_extraction_rules.xml`, guarded by `SeguridadConfigTest`).
- Cleartext HTTP is blocked (`res/xml/network_security_config.xml`); `NewsArticle.cleanUrl` upgrades scraped `http://` URLs to HTTPS.
- HTTP logging is debug-only with auth headers redacted (`RetrofitNetworkClient.loggingInterceptor`).
- **Release uses R8:** `isMinifyEnabled` and `isShrinkResources` are on, with rules in `app/proguard-rules.pro`. These keep the Moshi reflection models (`data/remote/model`) and the `@JavascriptInterface` methods, and strip `Log.v/d/i`.
  - Upload `mapping.txt` to Play.
  - To test the minified build on a phone next to the debug app: `./gradlew assembleRelease -PpruebaR8` (id `…agtech.r8`, debug-signed).
  - Release signing comes only from the env vars `KEYSTORE_PATH`, `STORE_PASSWORD`, `KEY_ALIAS` and `KEY_PASSWORD`. Without them the release is unsigned.
- **Permissions:** INTERNET, FINE/COARSE location (foreground only) and POST_NOTIFICATIONS. WorkManager's FOREGROUND_SERVICE is removed with `tools:node="remove"`. Unused libraries (Firebase AI, App Check, Google Maps) are commented out.
- The **Windy WebView** (`ClienteWindy`) only navigates inside https `*.windy.com`; other links open in the external browser. File and content access are off.
- `SeguridadConfigTest` guards: HTTPS-only, the exact permission set, R8 enabled, and no credentials in `.env.example`.
- Any Kotlin value interpolated into a script sent to a WebView must go through `jsString()` (`ui/components/mapa/GisMapController.kt`); structured data goes as a JSON string that the page `JSON.parse`s. In the map page, user text (lote names) is set with `textContent`, never `innerHTML`.
- The GIS map WebView only loads its own page from app assets (`WebViewAssetLoader` under `MAP_WEBVIEW_ORIGIN`), never navigates away, and `TeselasMapa` blocks every request that is not to an allowlisted tile server. The page → app channel is `WebViewCompat.addWebMessageListener` restricted to that origin (JavascriptInterface only as a fallback for very old WebViews).

## Architecture

Package root is `com.example` (namespace), applicationId `com.aistudio.granex.agtech`.

- **Shared code (`:shared`):** files moved from `:app` keep their package, so Android imports didn't change.
  - Code in `commonMain` can't use `java.*`, `android.*`, `Math.*`, `String.format` or JVM-only collection APIs (`MutableMap.merge`, `toSortedMap`). Use the helpers in `utils/Comun.kt` instead: `radianes`/`grados`, `FechasIso`, `formatoDecimal`.
  - Pure tests live in `shared/src/commonTest` and use `kotlin.test`, where the assertion message goes last.
- **Web app (`:webApp`):** keeps the Android patterns.
  - `ContenedorWeb` plays the role of `AppContainer`. ViewModels are created in `GranexWeb` with explicit keys (Kotlin/JS has no `qualifiedName`) and expose StateFlow with sealed states.
  - Layout adapts by `LocalClaseAncho`: COMPACTA (< 600 dp) uses a bottom bar and one column; MEDIANA (600–1199 dp) a rail and two columns; EXPANDIDA (≥ 1200 dp) a side menu and three columns.
  - Routes use the URL hash (`#/clima`).
  - DOM access lives behind `expect`/`actual` in `plataforma/Navegador.kt`, because Wasm and JS expose the DOM with different types.
  - The Satélite map reuses `app/src/main/assets/mapa` inside a same-origin iframe. Commands go in as `postMessage` JSON (`{metodo, args}` → `window.GRANEX.*`) and events come back the same way. The page only accepts messages from its parent window and from its own origin.
  - **Lots (web Satélite):**
    - `datos/LotesWeb` wraps `AlmacenLotesAjustes`. It exposes `lotes` and `pendientes` as StateFlows, and it is also the `AlmacenLotesLocal` given to `SincronizadorLotes`, so downloads and the logout wipe refresh the list and the map by themselves.
    - `SateliteWebViewModel` owns selection and editing (`EdicionWeb` over the shared `utils/EditorPoligono`, the same logic as Android's `SateliteViewModel`, tested in `EditorLoteTest`). It syncs after each save or delete.
    - The screen sends `setEdicion` only when `revision` changes (drags just update `areaEnVivo`), and `setLotes` with the edited lot hidden. Tapping the first vertex of a valid polygon opens the save dialog.
    - The GeoJSON comes from `utils/GeoJsonLote`, in the same format as `AgroSatRepository.generarGeoJson`.
    - Saving detects the province like Android: the shared `ServicioProvincias` (Nominatim `/reverse`, `zoom=5`, one user-triggered request, 10 s cap, in-memory cache). A province the user typed is never overwritten.
    - Each `listo` from the map page bumps `SateliteWebViewModel.listo` (a generation counter). The browser reloads an iframe that moves in the DOM (`movableContentOf` across width classes), and the new generation makes every effect resend its state.
  - **Scan (web Satélite):** `EscaneoWebViewModel` follows the selected lot. It needs a session, and the Edge Function rejects anonymous calls; without one, the panel says so and links to Cuenta.
    - It reuses the shared `SentinelGranex`, `EscaneoLote` and `AnalisisRelieve`, with the views INDICE (useful dates, NDVI/NDRE/GNDVI, Absoluto/Zonas, vigor zones), FOTO and RELIEVE. Downloads are cached in memory per lot+`modificadoEn`+date.
    - PNGs are decoded by `plataforma.decodificarPng` with `createImageBitmap` (`premultiplyAlpha: none`, `colorSpaceConversion: none`). Kotlin/JS's `js()` only parses ES5, hence `.then` there.
    - Map layers come from the shared `utils/CapaMapaEscaneo` (`CapaMapaEscaneoTest`), in the same JSON as Android's `capaSentinelJson`. The JSON is built once per state (`remember`) and sent as `setCapa` (`"null"` clears it).
    - Date comparison (`compararCon`, shared `EscaneoLote.comparar`, map layer `CapaMapaEscaneo.cambio`, ±`ESCALA_CAMBIO`) and the index series (tap a point to open that date) work like Android.
  - **Prescriptions (web Satélite):** `PrescripcionWebViewModel` + `pantallas/SatelitePrescripcion.kt`, the same flow as `PrescripcionViewModel` (bases CAMPANAS / FECHA / RELIEVE, monitor profile, zone count with the recommendation, machine grid, doses per zone). It calls `SentinelGranex` directly, decodes the PNGs with `decodificarPng` (same channel formulas as `SentinelBackendGranex`) and caches campaigns, relief and images in memory per lot + `modificadoEn`. Zones are drawn with `GRANEX.setZonas` (the scan layer is hidden meanwhile); another lot or drawing closes it. Files download through `Navegador.descargarArchivo` (Blob + `a[download]`): the monitor ZIP with LEEME, the 4 loose Cuffia files (one by one, 400 ms apart) or every format. Not on the web yet: yield maps, soil analysis and suggested doses (Android only).
  - **Edge Function CORS:** supabase-kt's `functions.invoke` sends `x-region` and `X-Supabase-Client-Platform(-Version)` besides `apikey`/`authorization`/`x-client-info`/`content-type`. Every function's `Access-Control-Allow-Headers` must list all of them, or the browser gets a 200 preflight and never sends the POST (the web scan failed with "No se pudieron obtener las fechas… Revisá la conexión"). Deploy from this machine with `D:\USUARIO\dev\tmp\scripts\desplegar_funcion.py <name> <files…>` (Management API, token from `D:\USUARIO\claves\granex-config.txt`, `verify_jwt` on); `logs_supabase.py <source> <hours ≤ 24>` reads `function_edge_logs` / `function_logs` / `auth_logs`.
  - Only APIs that allow CORS are called from the browser. RSS and the A3 futures (CEM has no CORS) go through the Edge Function `publico`; without a backend the UI says so instead of showing invented data. Secrets are never stored in the browser.
  - **Edge Function `publico`** (`supabase/functions/publico`, no session needed: the public key alone passes Supabase's gateway, sent as `apikey` + `Authorization: Bearer` by `ContenedorWeb`):
    - `GET /publico/noticias`: reads the 8 feeds of `FUENTES` (a copy of `FUENTES_NOTICIAS`: keep them equal) in parallel with `rss.ts`, a regex RSS reader with the same rules as Android's `LectorRss` (own-domain https links, sponsored content dropped, titles ≥ 8 chars, charset from the XML declaration). Returns `{generado, notas, fallidas}`; no notes at all → 502, never invented ones.
    - `GET /publico/a3/api/v2/closing-prices?…`: forwards only validated parameters (the 3 `… Dolar MATba` products, FUT, ROFX, dates, page ≤ 10, pageSize ≤ 300) to the CEM, so the shared `ServicioFuturosA3` works unchanged with `base` = the function.
    - It is not an open proxy (fixed destinations only), caches in memory (news 15 min, futures 30 min, one upstream call for concurrent requests) and limits 60 requests/min per IP and instance.
    - Local test with Node (no Deno here): `D:\USUARIO\dev\tmp\ts-prueba\probar_publico.mjs <function folder>` transpiles with TypeScript and calls `atender()` against the real sources.
  - **Web Finanzas futures:** `FinanzasWebViewModel` loads `ServicioFuturosA3` through `publico` + `FuturosA3.vigentes` (`EstadoFuturos`, `SinServidor` without a backend); today's date comes from `FechasIso.deArgentina` (UTC−3, no time-zone database).
  - **Web Finanzas layout:** dollars and futures are separate sections, each with its own state and source line. `GrillaPareja` spreads items evenly over the rows (7 dollars: 2 per row on a phone, 4 + 3 on a tablet, all 7 in one row on a monitor; never 6 + 1), and cards below 240 dp stack sell/buy. Dollars are ordered for the producer (`ORDEN_DOLARES`: oficial, mayorista, MEP, CCL, blue, cripto, tarjeta). Futures are one card per grain with its 3 positions.
  - **Web Novedades:** `NovedadesWebViewModel` over `ServicioNoticiasGranex`, classified with the shared `ClasificadorNoticias` (`FuentesNoticias.kt` moved to `:shared`, same package; `normalizar` strips accents without `java.text.Normalizer`; `ClasificadorNoticiasComunTest`). Theme chips like Android, cards open the article in a new tab. No cover images: the media CDNs don't send CORS. Without a backend or on error it lists the outlets to open directly.
  - **Mercado history (web):** `MercadoWebViewModel` loads granos.ar `/pizarra/historico?dias=365` (ARS/t per session) and argentinadatos' wholesale dollar in parallel; the shared `utils/HistorialPizarra` (`HistorialPizarraTest`) converts with each day's buying rate or the last earlier one, and drops sessions without price or rate. The panel uses the shared `AgregacionPrecios` with `RangoHistorial` (7 días, 30 días, 3 meses, and 1 año = `Granularidad.ANUAL`, web only), drawn by `GraficoPrecios`. When the day's pizarra has no price for a grain (granos.ar publishes the date before the Cámara's prices), the table and the margin calculator use that grain's last priced session from the history and say so (`preciosDeReferencia`); without it the calculator fell to US$ 0.
  - **Security (web):**
    - `index.html` carries a strict CSP `<meta>`: own scripts only, no inline scripts or eval (`'wasm-unsafe-eval'` only). Its `connect-src` lists the public APIs (dolarapi, Open-Meteo forecast and geocoding, granos.ar, argentinadatos, Nominatim) plus the Supabase origin, and its `frame-src` lists `'self'` plus Windy. A new external host must be added there, or the browser blocks it.
    - Startup code (saved theme, service worker registration, the "new version" notice) lives in `inicio.js`, never inline.
    - Hosting headers (`webApp/pwa/hosting/vercel.json`, `firebase.json`) add `frame-ancestors`, HSTS, COOP, `X-Frame-Options` and `Permissions-Policy`. Keep both files in sync.
    - Third-party iframes use `MarcoWeb(externo = true)`, which adds a sandbox (no top navigation) and a referrer policy. `MarcoWeb` only accepts messages from its own iframe window and the app's origin.
    - `Navegador.abrirEnPestana` only opens URLs that pass `utils/esUrlExternaSegura` (in `:shared`, tested in `UrlSeguraTest`).
    - **Publishing:**
      - `GRANEX_EMAIL_SOPORTE`, `GRANEX_URL_PUBLICA` and `SUPABASE_*` come from env or `local.properties` (`granex.emailSoporte`, `granex.urlPublica`). They fill `__EMAIL_SOPORTE__` / `__URL_PUBLICA__` in `index.html`, `legal/*.html` and `robots.txt`.
      - A line whose value is missing is dropped, so each placeholder must sit on a self-contained line. `distribucionPwa` warns `AVISO para publicar` for each missing value.
      - The legal pages (`resources/legal/`, script-free with their own CSP) are opened through `Navegador.abrirPaginaPropia(PaginaPropia)`, from Acerca de and from account creation. Keep their content in sync with `web/privacidad.html` / `web/terminos.html` and with what the app really does.
      - `404.html` and `robots.txt` ship at the root. `inicio.js` shows a "Recargar" notice if the app hasn't loaded after 45 s or one of its own scripts fails.
      - Hashed webpack files get a one-year `immutable` cache. Checklist: `docs/web/DESPLIEGUE.md` §0.
    - localStorage holds preferences (last city, `web_tema`, `web_menu`), the Supabase session (like supabase-js; protected by the CSP), the offline lot cache (`lotes_cache_v1`) and the Agenda (`agenda_v1`, wiped on logout). It never holds third-party credentials.
  - **Look and feel (web):**
    - Compose mounts in `<div id="granex">`, not in `<body>`. That keeps the HTML loading screen and notices visible.
    - The font is Inter. The weights 400, 500, 600 and 700 are subset to Latin-1, general punctuation, arrows and ≤ ≥ ≈. They live in `composeResources/font`, with the OFL license in `resources/licencias`. Use tabular numbers (`tnum`). Don't add glyphs outside the subset without regenerating the fonts.
    - The loading screen stays until `fuentesListas()` reports that every weight has loaded.
    - Theme: `ModoTema` (Automático / Claro / Oscuro) is saved as `web_tema`. The side menu shows a segmented selector, the rail a toggle and the phone a ⋮ menu. `TemaGranexWeb` syncs `theme-color`.
    - Desktop side menu (`MenuLateral.kt`, `NavegacionEscritorio`): `ModoMenu` FIJO or AL_PASAR is saved as `web_menu`, with a "Menú fijo" switch in the menu footer and a pin button in the rail.
      - AL_PASAR: content reserves only the 80 dp rail. On hover, or keyboard focus, after 120 ms the menu opens to 248 dp over the content with a shadow, without moving it.
      - Widths animate with `animateDpAsState` (220 ms; `snap()` if `prefers-reduced-motion`). Icons sit in a fixed 56 dp slot, so they don't move while the menu opens.
      - The open menu is drawn in the canvas, below any iframe: keep iframes out of the first 248 dp.
    - Iframes (map, Windy) are HTML above the Compose canvas, so a dialog or dropdown over them would be hidden. Every dialog or menu that can overlap a map calls `TaparMarcos()` (`plataforma/Navegador.kt`): while any is open, `MarcoWeb` sets its iframe to `visibility: hidden`, keeping its state.
    - Graphics follow the Android look: `ui/Graficos.kt` holds `TituloSeccion`/`IconoEnCirculo` (section headers), `TarjetaMetrica` (weather tiles with the same agronomic hints as `DashboardClimaRadar`), `TarjetaUv` (WHO scale, `NivelUv`), `InsigniaVariacion`, `IconoGrano` and `aspectoClima` (WMO code + `is_day`). Charts are drawn with Canvas, with no chart library: `GraficoHorario` (next 24 h of temperature and rain), `BarraRango` (weekly temperature bars) and `BarraProporciones` (vigor and relief classes).
      - Material icons outside core (sun, drop, wind…) are vector paths in `ui/Iconos.kt`. Grain icons in `ui/IconosGranos.kt` are generated from `ic_grano_*.xml`; regenerate them, don't edit by hand. `GranoWeb` has the same tints as Android's `Grano`, chosen through `LocalTemaOscuro`.
      - The shared `ServicioPronostico` uses `ecmwf_ifs` like Android, adds `cloud_cover`, `is_day` and hourly values, and fetches UV separately (`uv()`, without `models`). `riesgoIncendio` lives in `:shared` `ClimaComun`.
    - Use `Modifier.mano()` (hand cursor) on everything clickable. Use `BotonIcono` (with tooltip) for icon buttons. Use `PanelEsqueleto` for loading states.
    - `LocalConectado` shows "Sin conexión" in the header, and data reloads when the connection comes back.

- **No DI framework.** `GranexApplication` (registered in the manifest) owns an `AppContainer` with process-wide lazy singletons: Room DAO and all repositories (they hold in-memory caches/state, e.g. `FinancialRepository` is shared by Finanzas and Mercado). `GRANEXMainApp()` in `MainActivity.kt` creates every ViewModel with `viewModel { ... }` (Activity-scoped, survives rotation) from the container and passes them into screens. New repositories go in `AppContainer`; new ViewModels are wired in `GRANEXMainApp()`.
- **UI state:** user input and dialog/selection flags use `rememberSaveable`; screen data lives in the ViewModels. Collect flows with `collectAsStateWithLifecycle()`.
- **Same proportions on every phone** (`ui/components/Adaptable.kt`):
  - `GRANEXTheme` wraps everything in `EscalaPorPantalla`. The app is laid out as on the 411 dp Pixel it was designed on (`ANCHO_DISENO_DP`) and scaled as a whole to the phone: density = real density × (shortest screen side / 411), clamped to 0.7–1.3.
  - `MainActivity.attachBaseContext` applies the same scale to the Activity configuration (`EscalaPantalla.contexto`: `densityDpi`, `fontScale` 1, screen dp). Every separate window (ModalBottomSheet, dialogs, menus, popups) builds its own Compose root that re-provides the context's density and font scale, so with only `EscalaPorPantalla` the Clima and Mercado sheets came out deformed on a 384 dp Xiaomi with font 1.45×. With the configuration already scaled, `EscalaPorPantalla` computes 1× on devices and only matters in Robolectric tests.
  - `fontScale` is forced to 1. Text follows the same scale, not the system font size: on a 360 dp phone with font 1.3× the text grew and the boxes didn't. The owner asked for this ("que las proporciones se agranden o achiquen en base al celular"), so don't reintroduce font-scale-dependent layouts.
  - Landscape keeps the portrait scale (shortest side) and just gets more width.
  - Nothing else may read `LocalConfiguration.screenWidthDp` for layout; use the constraints. Screenshot tests (`FinanzasMaquetacionScreenshotTest`, `AjustesMaquetacionScreenshotTest`) check 320/360 dp, font 1.15/1.3× and landscape: all must look like the Pixel.
  - Helpers for wider screens (landscape, tablets):
    - `GrillaAdaptable(anchoMinimo)`: as many columns as fit, equal heights per row. Finanzas shows 2 per row on phones and 5 in landscape.
    - `LadoALadoOApilados`: two things side by side if they fit, else stacked. Don't use `FlowRow` inside an `IntrinsicSize.Min` row: its intrinsic height ignores wrapping, so the card lost its last line.
    - The 4-column tables (ROFEX, Mercado history) switch to two-line rows below ~320–330 dp.
    - `GranexHeader` drops the "GRANEX" wordmark below 150 dp of title area.
- **Side effects belong in ViewModels, not composables:** `WeatherViewModel` fires weather notifications once per new `dashboard.lastUpdated` and applies the startup GPS location only once (`usarUbicacionInicial`). Map fly-to targets are a consumable `DestinoMapa`.
- **Locality search (Clima and Satélite):**
  - Suggestions while typing come from `data/repository/GeocodificadorLocalidades`, which uses **Photon** (`photon.komoot.io`). Nominatim's usage policy forbids client-side autocomplete.
  - Results are filtered to `place:*` tags, show Argentina first, and are biased to a point. Each result carries a `TipoLocalidad` (from OSM `place`; the `extent` only promotes a city to `CIUDAD_GRANDE`), which sets the map zoom: closer for towns, so their label is readable.

      - **Fences and roads first** (`vra/DetectorAlambrados`): an edge map (max over layers of the neighbour difference across each pixel), a Hough transform over the strong edges near the region only (its bbox + 27 px; `fuertesCerca`: ≥ max(0.06, p85), with p85 the lower of the zone's and the whole box's; a river and a town elsewhere in the box once pushed the threshold to 0.26 against fences of 0.10–0.15, so a real 18.5 ha lot got no lines and lost its headlands) and, per peak, the longest continuous run (≥ 15 px = 150 m, gaps ≤ 3 px). A run lying mostly on the ±2 px band of a stronger line is dropped (a line tilted 5–10° across a fence's edge band used to cut a wedge off the lot). Lines that run within 25 px of the region without crossing its core (region eroded 2 px) bound it as half-planes on the seed's side; a line whose far side (3–8 px beyond, along its run) is ≥ 40 % like the region is an interior canal or track, not a fence (a real 1 km straight drain cut a bare lot; fences scored ≤ 0.34); while the cell covers < 75 % of the region, the line that leaves out the most is dropped (an interior canal). Every side of the cell must lie on strong edges for ≥ 60 % of its length, or its line is dropped and the cell rebuilt (short straight bits of a wavy wet-strip border). If the cell closes (no side on the box border) and is ≤ 1.7 × the region, the lot is that convex cell. Up to 2.4 × is accepted when every side lies on strong edges for ≥ 80 % of its length and no line parallel to a side runs inside the cell (≥ 3 px from the sides) for ≥ 40 % of √(cell area): that would be an inner fence between two lots. A real 97 ha lot with a differently tilled half grew a 51 ha, 15-vertex blob (cell 1.94 ×) before this; now it is the 4-fence rectangle (on real bare-soil lots the inner fences are often too faint, so the traced region is still what most taps get): the wet strip the crop didn't join gets in, and a leak through a gate into the farmstead gets cut. Otherwise the traced region below is used. Wavy wet-strip borders don't make lines, so they don't cut the lot.

    - In CAMPANAS mode no single-date image is downloaded. Flow tested in `PrescripcionCampanasTest`.
    - RELIEVE zones by height above the lot's lowest point (`RelieveLote.comoImagen`, metres in all three channels), so zone 1 = the lowest ground.
      - `nombreValor` is "Altura (m)" and the files are named with "relieve".
      - The coefficient of variation means nothing for heights, so the recommendation treats the lot as uniform only when it is plano (`Zonificador.cantidadRecomendada`).
    - `rezonificar` cancels the previous zoning job before checking the new base, so a slow result from the old base never overwrites the new one.
  - `Zonificador` (pure, tested in `VraTest`) resamples to a lat/lon machine grid (cell 10–30 m), classifies (k-means or quantiles), smooths, merges patches below the minimum area and raises it until the monitor's polygon limit fits, then traces zone outlines (exterior clockwise, holes counter-clockwise).

  - **Account deletion** (Google Play and the App Store require it in the app): "Eliminar cuenta" under the session panel (Android and web), with a confirmation dialog. `ControladorCuenta.eliminarCuenta` → `Autenticacion.eliminarCuenta` → Edge Function `supabase/functions/cuenta` (`{accion: "eliminar"}`), which checks the user, removes their Storage folder and deletes the Auth user with the service key that Supabase injects into functions (never shipped). Table rows go by `on delete cascade`. Only on success are the device's lots (`SincronizadorLotes.olvidarCuenta`, pending ones too) and Android's agronomy files (`borrarDatosLocales`) wiped. `web/eliminar-cuenta.html` explains how to do it without the app (Play's deletion URL).
  - Support email: **supportgranex@gmail.com** (`EMAIL_SOPORTE` and `EnlaceSoporte` in `ui/components/EnlaceExterno.kt`, the "Ayuda y soporte" card in Ajustes, `CONFIG.emailSoporte` in `web/js/main.js`, and the default of `GRANEX_EMAIL_SOPORTE` for the web app's legal pages). Publishing steps and Play Console texts: `docs/publicacion/GOOGLE_PLAY.md`.
  - Without a configured backend, deletes stay physical, as before.
- `granex_database_schema.sql` is a MySQL reference schema for a backend; it is not used by the app at runtime.
